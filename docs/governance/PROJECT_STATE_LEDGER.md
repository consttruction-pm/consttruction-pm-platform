## Agent 3 checkpoint — Issue #1799, slice 4 (`agent3/report-parameters-2026-11`, PR pending)

- **Baseline:** `main` @ `bca5800` (PDF export merged as PR #1803; `da22846` is Agent 1's document-bytes workspace merge).
- **Parameterized report definitions (Workstream 3):** a definition can bind a typed subset of the subject's server-owned parameter catalogue. Activities expose `status`, `activity_type`, `actual_start_from` and `actual_start_to`; resources expose `resource_type` and `is_active`; risks expose `status`, `category` and `min_score`. Bindings store only key/required/default; labels, types, enum choices and filter semantics live in `report_parameters.py`, so a client cannot widen an enum or inject a label.
- **Run semantics and provenance:** `POST .../reports/{id}/run` accepts `{"parameters": {...}}`; values are canonicalized and the run stores resolved `parameters` plus `parameter_sources` (`explicit`/`default`). Filtering applies to the stored snapshot rows only — no row, column or aggregate is invented. Missing required, unknown, invalid and duplicate/non-object payloads fail closed with `REPORT_PARAMETER_REQUIRED`, `REPORT_PARAMETER_UNKNOWN`, `REPORT_PARAMETER_INVALID` and `INVALID_REPORT_PARAMETER_LIST`/`REPORT_PARAMETER_DUPLICATED`.
- **Idempotency and revisions:** bindings are part of the definition fingerprint, so reusing a key with changed parameters returns 409 `REPORT_IDEMPOTENCY_KEY_REUSE`; a parameter change through update appends a revision and audit event.
- **Migration (Workstream 5):** `SQLiteReportStore.initialize()` adds `parameters_json` to the definition and run tables with empty defaults; a test creates the pre-parameter schema, inserts a definition/run, runs `initialize()`, reads both unchanged, then writes and rereads a parameterized definition.
- **Tests:** new `tests/test_report_parameters.py` (7 tests) covers catalogue exposure, explicit/default provenance, all-subject filtering, required/unknown/invalid/duplicate failures, fingerprint reuse and the SQLite migration. Full suite: **3613 passed, 147 skipped** without a DSN and **3801 passed, 1 skipped** with both PostgreSQL DSN variables.
- **Not claimed:** durable scheduled runs/retry/delivery checksums, a PostgreSQL report store (the register remains SQLite-only) and Web parameter/downstream wiring (Agent 1's surface) remain open.

## Durable report schedules slice — 2026-11-12 (merged; PR #1805)

- **Base:** branch cut from merged `main` `842208d` (parameterized report definitions/runs); squash-merged to `main` as `89b1d1d` via PR #1805. Scope is Issue #1799 Workstream 3: durable scheduled report jobs, without a second scheduler and without transport delivery that needs external credentials.
- **Durable model:** new `project_report_schedule` table stores cadence (`daily|weekly|monthly`), local `run_time`, IANA `timezone`, `weekday`/`day_of_month`, `project_revision`, `export_format`, `locale`, explicit `parameters`, `enabled`, optimistic `revision`, `next_run_at`, `last_run_at`, `last_status`, `last_error`, `attempts`, claim token/lease and timestamps. `SQLiteReportScheduleStore.initialize()` also adds `project_revision` to databases created by the earlier untracked build, so no existing database is dropped or rebuilt.
- **Next occurrence:** `compute_next_run` converts local wall clock through `zoneinfo` to UTC with strict `>` semantics; DST gaps map forward and repeated times use `fold=0`. Covered for daily/weekly/monthly and both 2026 New York DST transitions.
- **Execution:** `ReportScheduleRunner.run_due(now, worker_id, limit)` claims enabled due rows with a random token and lease. Run identity is deterministic (`RUN-SCH-{schedule_id}-{scheduled_for UTC}`) and `generated_at` is the scheduled instant, so a crash after the immutable run is saved but before completion reuses it instead of duplicating it. Success records the export SHA-256, resets attempts and advances the cadence; failure records bounded error text, increments attempts and retries with exponential backoff (5-minute base, 60-minute cap). A re-claimed lease can no longer complete/fail the row (`REPORT_SCHEDULE_CLAIM_LOST`).
- **Snapshot semantics:** a schedule captures `project_revision` at create/update and materializes at that revision. Only explicit parameter values are stored; defaults are re-resolved at execution, so the run records real `explicit`/`default` provenance. Scheduled materialization goes through a new trusted `ReportApplicationService.run_scheduled(...)`; it revalidates inputs and definition existence but is not an HTTP authorization bypass (no user context exists on the deployment trigger).
- **HTTP/API:** `GET|POST .../reports/{id}/schedules`, `GET|PUT|PATCH|DELETE .../schedules/{schedule_id}`, `GET .../schedules/{schedule_id}/history`. Reads need project-read; writes need project-write and same scope; stale updates/deletes are `409 REPORT_SCHEDULE_REVISION_CONFLICT`; duplicates are `409 REPORT_SCHEDULE_ALREADY_EXISTS`. Catalogue advertises `schedule_cadences`.
- **Audit separation:** schedule events use `entity_type = 'report_schedule'`; `definition_history` now filters `entity_type = 'report'`, so schedule events cannot appear in report history. Audit revisions use the next free key, so delete → re-create with the same id remains append-only instead of colliding.
