## Assignment window checkpoint — 2026-10-26 (`e6dbc426`; PR #1582 branch; not merged)

- **Delivered on the branch:** `place_resource_dependent_assignments` binds the authoritative CPM `result.early_activities` and `result.late_activities` of the same schedule run, derives early/late assignment windows and returns them with `assignment_float_working_days` and `placement_direction` in the Schedule Query placement payload. `placement_direction="LATE"` implements a separate backward priority pass from the late dates. The evaluator selects `LATE` automatically when the schedule mode is `ALAP`, so assignments follow the same dates as the activities; an `EARLIEST` schedule keeps the previous `EARLY` behavior and output.
- **Contract highlights:** the early window is the first run of consecutive positive-capacity resource dates starting on or after the CPM activity early start; the late window is the last such run starting on or before the CPM activity late start (it may finish after that start, mirroring the documented rule that a nondriving assignment may finish after the activity). When a zero-float activity starts on a date without positive resource capacity, the late window falls back to the first run at or after that shared start instead of inventing an earlier window. A driving assignment stays fixed at the authoritative activity dates, reports those dates as both windows and carries zero assignment float. Missing early/late dates, negative float, unavailable late windows and late-capacity exhaustion are explicit diagnostics; a truncated backward search says so and the candidate limit is hash-bound. Assignment float is measured on the resource calendar and is never clamped; a negative value means the two independent priority passes assign shared capacity differently. The module never recalculates CPM or uses placed assignment dates to infer activity late dates.
