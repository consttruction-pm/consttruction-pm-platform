# CUBI full-stack local preview

This document describes the real, reproducible local preview used to inspect the
CUBI Web workspace against the real WSGI API, SQLite persistence and the Shared
Domain/Calculation Core. It is **not production**, it uses **demo data only**, and
no external preview has been published.

## Status and external blocker

- External preview: **not available**. The GitHub repository reports
  `has_pages=false`; there is no GitHub Pages site to update. No deployment was
  performed. The local preview below is the inspectable replacement.
- A production login route does not exist in the product. The preview adds a
  loopback-only demo identity page; it is not a production credential system.
- The CUBISITE workbook is not present in the repository, so official
  weights/completion percentages are not available and are not invented here.

## One command

```bash
cd apps/web
npm install          # first run only
npm run preview:full
```

Then open:

- Login: <http://127.0.0.1:4174/preview/login>
- Workspace: <http://127.0.0.1:4174/app>
- Health: <http://127.0.0.1:4174/preview/health>
- Landing page: <http://127.0.0.1:4174/>

`preview:full` builds the Web client with the repository TypeScript toolchain,
then starts the Python preview composition. It uses `py -3` on Windows and
`python3` elsewhere; set `CUBI_PYTHON` to override the interpreter.

Equivalent direct command from the repository root:

```bash
PYTHONPATH=src py -3 -m construction_pm.preview --web-root apps/web --port 4174
```

Add `--reset` once to rebuild the guarded demo database (the previous database is
backed up under `.preview/backups/`). Without `--reset`, saved layouts, settings
and sessions continue across restarts; in-memory demo sessions are recreated when
the process restarts.

## What is real in the preview

| Layer | Implementation |
| --- | --- |
| Web client | Built CUBI Web assets (`apps/web/dist/...`) served by the preview. |
| HTTP | Real `ProjectLifecycleWsgiApp` routes, not a mock server. |
| Persistence | Real SQLite repositories for activities, relationships, calendars, settings, layouts, field registry, UDFs, snapshots and the mapping registry. |
| Calculation | Published immutable snapshot + `POST /api/v1/schedule/query` through the Shared Domain/Calculation Core. Dates, float and critical flags are not computed in the browser. |
| Presentation | Persisted `p6-layout.v1` revisions and `p6-field-registry.v1` fields; optimistic layout revisions. |
| Formulas | The workspace formula editor posts expressions to `POST /api/projects/{project}/p6/formulas/{registry_version}`. Parsing, dependency analysis, type inference and fail-closed field-type diagnostics come from the Shared Core; the browser does not evaluate formulas. |
| Resource capacity | Typed effective-dated Resource Max Units/Time persisted per tenant/project/revision through `SQLiteP6ResourceCapacityRepository`; read through `GET /api/projects/{project}/p6/resource-capacities[/{resource_id}]`, written through `POST /api/projects/{project}/p6/resource-capacities`, and converted for a period through `POST /api/projects/{project}/p6/resource-capacities/{resource_id}/resolve`. Ceilings come from explicit registered segments, never from assignment `units_per_time` or a calendar default. |
| Interchange | Real provider XML codec and persisted mapping registry through `POST .../p6/interchange/PRIMAVERA_XML/{export,import}`, exposed in the Web `Project → Import / Export` panel. Export is generated by the server codec from loaded activity facts; import maps rows server-side and shows canonical values, preserved provider object and loss warnings without writing to activities. |
| Sessions | In-memory opaque demo sessions (8-hour TTL), server-enforced role policy. |
| Dates | Schedule dates are stored and calculated as canonical ISO Gregorian values. The workspace calendar-mode toggle renders Jalali labels with a UTC-based presentation conversion only; stored and calculated dates do not change. In DATE_BASED schedule settings with the Jalali calendar system selected, start/finish accept typed Jalali dates (Persian, Arabic-Indic or Latin digits), convert them to canonical ISO before the API call, and reject impossible dates without persisting anything. |
| Database safety | The preview refuses foreign/stale SQLite files and rebuilds only its own application ID, marker and seed version. |

Only the guarded demo database, demo identities and curated fixtures are
preview-specific. Scheduling and authorization decisions remain in the product
code paths.

## Demo identities

The login page offers three fixture-only identities. Roles are enforced by the
real authorization policy after login:

| Identity | Role | Expected behavior |
| --- | --- | --- |
| `preview-planner` | planner | Read, save layout/settings, publish snapshots, import exchange data. |
| `preview-viewer` | viewer | Read-only; layout/settings writes, snapshot publication and import return 403. |
| `preview-admin` | project administrator | Planner capabilities plus project creation where the Web exposes it. |

The fixed banner on every authenticated page reads
`LOCAL PREVIEW · DEMO DATA · NOT PRODUCTION` and identifies the signed-in demo
user. There is no password, no production identity and no external service call.

RPS relationships include FS, SS with working-day lag and a fan-out from A130.
The seeded snapshots are published through the same snapshot publisher used by
the product, so the workspace/Gantt reads persisted schedule facts and the run
panel re-publishes and re-queries the current saved state.

RPS also seeds two registered capacity segments for `RPS-CIVIL-CREW`: 8 units/day

computes the content identity, derives the source from the signed-in user, closes
the prior open-ended segment the day before the new start date, keeps the prior

The create-project form creates an empty project with the curated 20-field

calendar and no invented activities or capacity.

## AI action execution in the preview

The preview composes the **real** AI action runtime, not a mock. The typed
`activity.create` and `activity.update` tools are exposed in the workspace
**AI Assistant · Actions** panel. The flow is:

1. The editor prepares a proposal; the server validates the payload, checks the
   current project revision and the exact-scope grant, and returns a durable
   `proposed` record. No project row is written yet.
2. A human explicitly approves or rejects the proposal. Approval is bound to the
   actor, proposal and project revision.
3. Execution is a separate explicit request. The runtime authorizes the exact
   tool/operation/domain grant again, writes the activity transactionally, then
   recalculates through the Shared Core snapshot/query path.
4. The panel displays the calculated start/finish, duration, project finish and
   snapshot identity returned by that recalculation. It never computes dates in
   the browser and never shows a fabricated result.
5. A stale project revision is rejected before mutation, and replaying a
   completed execution returns `409 AI_ACTION_PROPOSAL_NOT_APPROVED` without a
   second write.

Grants in the preview are default-deny and rebuilt from the persisted project
rows on every decision: only the `planner` and `project_admin` demo personas
receive the two activity tools, and an advanced project revision revokes the
older grant immediately. Viewers, unknown subjects, other resource domains and
every other tool/operation are denied. The natural-language assistant turn still
requires an external model provider; the chat panel reports that it is not
configured instead of inventing a reply.

## Automated verification

Run the repository browser E2E (Chrome or Edge must be installed; set
`CHROME_PATH` if the browser is not in a standard location):

```bash
cd apps/web
npm run test:e2e:preview
```

The script starts an isolated preview on a random loopback port with a temporary
SQLite database and a real headless browser. It verifies:

- health identity, landing page, unauthenticated `/app` redirect and session 401;
- the three demo personas and planner project selection;
- menus/submenus, persisted grid rows, Gantt rows and shared grid/Gantt selection;
- column hide/remove/add/reorder/width/pin/freeze through the real layout API,
  followed by a full reload and read-back;
- layout undo/redo: removing a column then undoing restores the persisted column
  set, redo reapplies the removal, every action appends a new revision instead of
  rewriting the append-only history, and undo remains available after a full
  reload through `GET .../p6/layouts/project/activity/revisions`;
- explicit revision restore: the revision picker offers only older revisions,
  restoring one reapplies its column set as a new head revision while preserving
  every prior revision in newest-first order;
- stale-write conflicts, both recovery branches: a competing API writer appends
  the next layout revision while the page still holds the previous head (the
  stale edit receives `IMMUTABLE_LAYOUT_REVISION`); then a second race advances
  the head by two revisions before the page writes (the stale edit receives
  `REVISION_CONFLICT`). In both cases the edit fails closed, the page shows the
  localized conflict notice and reloads the authoritative head, the competing
  presentation survives, and the lost race appends no revision;
- filter and numeric sort behavior, including an explicit empty state;
- WBS rollup navigation: the server returns a `wbs_summary` aggregated from the
  persisted WBS assignment and the schedule facts the read already projects
  (activity count, critical count, scheduled bounds, minimum total float).
  Clicking `2 Civil works` filters the grid and Gantt to exactly its 5 activities,
  shows the Jalali-formatted server bounds and the count `/ 14`, toggles off,
  re-selects, and clears through the explicit control. The browser derives no
  schedule value; a malformed summary fails closed with
  `INVALID_WORKSPACE_WBS_SUMMARY`;
- project settings/calendar read, save and revision increment;
- the scheduling-mode option offers both `EARLIEST` and `ALAP`; selecting
  `ALAP` persists through the settings API, and restoring `EARLIEST` appends a
  further revision. The Shared Core evaluator regression proves ALAP drives
  `LATE` resource-dependent placement, while EARLIEST keeps the `EARLY` default;
- append-only schedule-settings history and explicit restore: each save appends
  a revision row with its canonical payload and hash, `GET
  /api/projects/{p}/p6/schedule/settings/revisions` lists them newest-first, and
  the panel's history control restores a selected older revision by saving it as
  a new revision at the current expected revision. The E2E asserts revisions
  `3,2,1`, restores revision 1, and re-reads `4,3,2,1` with `EARLIEST` applied;
  `POST .../revisions` fails closed with `405 Method Not Allowed`, a tampered
  history hash fails closed with `SETTINGS_HASH_MISMATCH`, and an appended
  duplicate revision fails closed with `SETTINGS_HISTORY_CONFLICT`, rolling the
  settings write back to a savepoint (including inside a caller-owned
  transaction) so the current row cannot survive without its matching history;
  revision reads are capped at 50 rows by default;
- snapshot publication plus Shared Core query results and content hash;
- formula editor validation through the Shared Core authority: a valid numeric
  expression returns its dependency and result type, a context self-reference
  returns `FORMULA_SELF_REFERENCE`, and a registered duration field that has no
  safe formula representation returns
  `UNSUPPORTED_P6_FORMULA_FIELD_TYPE:duration` with no invented result type;
- typed resource capacity read, effective-dated profile, day→week conversion with
  an explicit 40 h/week factor, distinct immutable identities and a fail-closed
  404 for an unregistered resource;
- the Resources panel reads the seeded profile, registers a 10 units/day change
  effective 2026-11-01 with the close option, shows the prior open segment closed
  on 2026-10-31 without rewriting it, resolves 50 units/week on 2026-11-02 and an
  explicit out-of-range error, then re-reads the same three segments and 50
  units/week after a full browser reload;
- provider XML export/import round-trip through persisted mappings at the API level;
- the Project import/export panel exports all 14 activities through the server codec, downloads the generated document, re-imports it as 14 mapped rows, rejects an invalid document with `INVALID_XML` and no fabricated rows, and shows the viewer import denial without mapped rows;
- Jalali/Gregorian display toggle: 2026-10-07 renders as ۱۴۰۵/۰۷/۱۵ and the stored
  ISO value is unchanged when switching back;
- typed Jalali entry in DATE_BASED schedule settings: 2026-09-21 renders as
  1405/06/30, a typed `۱۴۰۵/۰۶/۳۰` persists as `2026-09-21`, an impossible
  `1405/13/01` surfaces `INVALID_PROJECT_START` without changing stored data, and
  the rejected entry does not leave a stale canonical value behind when the

- a 1024×768 compact desktop layout with navigation inside the viewport;

- admin-only project creation from the Web form, persisted project name, empty

## Manual walkthrough

1. Open `/preview/login` and choose **Planner**.
2. Select **Riverside Pump Station Upgrade**; inspect the activity grid and Gantt.
3. In **Project / WBS**, confirm each group shows its server-computed activity and
   critical counts plus scheduled bounds (or **Not scheduled**). Click
   `2 Civil works` and confirm the grid/Gantt show exactly its 5 activities and the
   selected count reads `5 / 14`; click again or press **All activities** to clear.
4. Hide, add, reorder, resize, pin or freeze columns; reload and confirm persistence.
   Remove a column, press **Undo** and confirm it returns; press **Redo** and confirm
   the removal returns. Choose an older revision in the revision picker and press
   **Restore** to confirm that revision is reapplied. Reload again and press **Undo**
   to confirm the prior persisted revision is restored; the history endpoint must
   show a new revision on top rather than rewritten rows.
5. Filter by `civil` or `civil completed`; sort by Id or Total Float.
6. Toggle **Jalali** and confirm dates change for display only; toggle back.
7. Open **Schedule → Schedule settings**, confirm `CUBI-RPS-CAL` and save. Set the
   calendar system to **Jalali**, confirm the start renders as `1405/06/30`, type
   `۱۴۰۵/۰۶/۳۰`, save and confirm the API still stores `2026-09-21`; try
   `1405/13/01` and confirm `INVALID_PROJECT_START`; switch back to Gregorian.
   Switch the mode to `ALAP` and save, then use the settings-history control to
   select an older revision and press **Restore**; confirm the panel reports the
   restored revision and that the history now shows one more revision on top
   (older revisions are preserved, never rewritten).
8. Open **Schedule → Run Schedule** and compare the returned A130 dates, float,
   critical flag and snapshot hash.
9. Open **Schedule → Formula editor**, enter
   `[activity.duration_percent_complete] / 100`, validate and confirm the
   authoritative dependency and result type. Then make the context field the
   referenced field and confirm `FORMULA_SELF_REFERENCE`; finally use the
   registered duration field and confirm the explicit
   `UNSUPPORTED_P6_FORMULA_FIELD_TYPE:duration` diagnostic.
10. Open **Project → Import / Export**, export the 14 loaded activities, download
    the server-generated document, paste it back and map it to confirm 14 canonical
    rows. Submit an invalid document and confirm an explicit `INVALID_XML` error
    with no rows.
11. Open **Resources → Max units / time**. Read the seeded 8 → 12 units/day
    profile, resolve 2026-10-16 as a 40-hour week and confirm 60. Register
    10 units/day from 2026-11-01 with the close option, confirm 2026-10-31 closes
    the prior open segment, and resolve 2026-11-02 as a week to confirm 50.
    Reload and confirm the three segments persist. The same values are readable
    through `GET /api/projects/preview-rps-01/p6/resource-capacities/RPS-CIVIL-CREW`
    with a planner session; an unregistered resource returns 404
    `RESOURCE_CAPACITY_NOT_REGISTERED`.
12. Switch the top-right language control to Persian and confirm RTL labels.
13. Sign out, sign in as **Viewer**, and confirm exports remain readable while an
    import is denied with an explicit permission error.
14. Sign out, sign in as **Admin**, create a project from the project-selection
    form, and confirm the new empty workspace, curated layout and persisted name.
15. Re-select **Riverside Pump Station Upgrade** and open **AI Assistant ·
    Actions**. Prepare an activity with a unique ID, a name and a 3 working-day
    duration. Confirm the proposal shows the current project revision and no
    activity exists yet. Press **Approve**, then **Execute approved action**;
    confirm the panel reports the saved-and-recalculated outcome with real
    calculated start/finish and snapshot identity. Reload and confirm the new row
    shows the same dates and the saved verification is still displayed. Replaying
    execution must be refused, and a project-revision change must mark the
    proposal stale. Signing in as Viewer must deny both proposal reads and
    writes with no project change.

## Known limitations

- No external preview URL/deployment is available; GitHub Pages is not enabled for
  this repository.
- Import is mapping/review only: the mapped rows are not persisted or applied to
  activities. Export covers the registered mapping fields (activity id and name),
  not every workspace column, and does not create a new project.
- Typed Jalali entry is available in DATE_BASED schedule settings when the project
  calendar system is Jalali; time-aware settings keep an ISO `datetime-local`
  control, and other workspace date cells remain read-only display values.
- The formula editor performs authoritative validation only. Saving formula
  definitions and binding calculated formula columns to persisted values are not
  exposed in this workspace slice. Registered `duration` fields fail closed with
  `UNSUPPORTED_P6_FORMULA_FIELD_TYPE:duration` because calendar-dependent
  duration arithmetic has no safe formula representation yet.
- The WBS surface is a flat persisted WBS grouping, not a hierarchy editor.
- Undo/redo and explicit revision restore currently cover the persisted layout
  presentation and schedule settings (append-only revisions plus durable
  history). Settings restore re-saves the selected older settings as a new
  revision; it is not an in-place rollback. Schedule-settings history begins
  when the history table is created: settings persisted before that upgrade have
  no backfilled revision rows. Activity, WBS and commercial undo/redo and a
  project-wide backup/restore UI are not implemented.
- Typed Resource Max Units/Time is implemented as domain + persistence + read and
  write APIs plus a Web panel. The panel appends effective changes and resolves
  periods; it does not provide bulk capacity import or a separate leveling
  editor, and it never computes capacity client-side.
- Assignment-level early/late windows and assignment float are now returned by
  the Shared Core placement result and are derived from the authoritative CPM
  early/late dates of the same run; the placement module never recomputes CPM.
  An `ALAP` schedule result places assignments backward automatically, while an
  `EARLIEST` result keeps the documented `EARLY` default. Backward placement
  also exists as an explicit Shared Core `placement_direction="LATE"` contract,
  but no persisted schedule option or Web control selects it independently yet.
- CUBISITE workbook-derived official weights, scoring or completion percentages
  are unavailable and must not be inferred from file counts.
