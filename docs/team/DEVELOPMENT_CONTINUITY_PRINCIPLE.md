# اصل اجرای توسعه در ChatGPT و بازگردانی نهایی به GitHub

**وضعیت:** اصل دائمی و الزام‌آور تیم  
**اعضای مشمول:** جلال، جواد، حسن  
**دامنه:** کلیه کارهای توسعه نرم‌افزار، تست، اصلاح، بازبینی، مستندسازی فنی و تکمیل وظایف پروژه Construction PM Platform

## اصل اصلی

از این پس **محیط اصلی انجام کارهای توسعه پروژه، ChatGPT به‌همراه محیط فایل و اجرای کد آن است** و GitHub محل نگهداری، نسخه‌بندی و دریافت خروجی نهایی خواهد بود.

برای **تمام وظایف توسعه**، روش استاندارد و الزام‌آور این است:
1. نسخه موردنیاز سورس، فایل یا ZIP پروژه در ChatGPT بارگذاری یا در محیط کاری ChatGPT آماده شود.
2. فایل‌های واقعی، ساختار پروژه و وابستگی‌های مرتبط در همین محیط بررسی شوند.
3. کدنویسی، اصلاح، refactor و مستندسازی فنی در همین محیط انجام شوند.
4. تست‌های واحد، یکپارچه، regression و تست‌های اختصاصی همان وظیفه که در این محیط قابل اجرا هستند، در همین محیط اجرا شوند.
5. خطاها تا حد ممکن در همین محیط شناسایی، اصلاح و مجدداً تست شوند.
6. کار تا تکمیل وظایف تعریف‌شده و تست‌های لازم ادامه پیدا کند و نسخه ناقص به‌عنوان نسخه نهایی به GitHub برگردانده نشود.
7. پس از تکمیل وظیفه و انجام/قبولی همه تست‌های لازم، فایل‌های نهایی به همراه commit/branch و مستندات تغییرات به GitHub بازگردانده و ذخیره شوند.

## زنجیره اجباری اجرای کار

**Upload/Prepare in ChatGPT → Inspect → Code → Run Tests → Fix → Re-test → Complete Task → Return Final Files/Commit to GitHub**

این زنجیره برای جلال، جواد و حسن و برای همه workstreamهای پروژه قاعده پیش‌فرض است.

## جایگاه GitHub و CI

GitHub محل **نسخه‌بندی، ذخیره‌سازی، اشتراک تغییرات، review و بازگردانی خروجی نهایی** است.

GitHub Actions، Hosted Runner و سایر CIها برای **تأیید runtime واقعی، regression نهایی و release gate** استفاده می‌شوند؛ اما نباید تنها محیط کدنویسی یا تنها محیط تست روزانه باشند.

خرابی GitHub/CI/Runner نباید به‌تنهایی باعث توقف توسعه شود.

## اصل تکمیل وظیفه

پیش از بازگردانی نسخه نهایی به GitHub، بسته کاری باید:
- پیاده‌سازی کامل داشته باشد.
- تست‌های مرتبط قابل اجرا در ChatGPT اجرا شده باشند.
- نتایج تست‌ها ثبت شده باشند.
- خطاهای کشف‌شده برطرف یا به‌طور صریح به‌عنوان blocker ثبت شده باشند.
- تغییرات با commit پایه قابل تطبیق باشند.
- محدودیت‌های محیط ChatGPT یا وابستگی‌های بیرونی مستند شده باشند.

**هیچ تستی که اجرا نشده است نباید passed، successful یا verified اعلام شود.**

## کارهای وابسته به زیرساخت بیرونی

اگر بخشی از کار به PostgreSQL واقعی، سرویس خارجی، credential، شبکه، production، runner یا زیرساخت دیگری نیاز دارد:
- بخش قابل اجرا ابتدا در ChatGPT پیاده‌سازی و تست شود.
- برای بخش قابل آزمون محلی از mock، fixture، test double یا محیط محلی مناسب استفاده شود.
- فقط همان بخش غیرقابل اجرا به‌عنوان runtime-pending علامت‌گذاری شود.
- پس از آماده شدن زیرساخت، runtime واقعی به‌عنوان gate نهایی اجرا شود.

این موضوع نباید باعث توقف بخش‌های مستقل توسعه شود.

## اصل بازگردانی نهایی

خروجی نهایی باید قابل بازیابی و قابل ردیابی باشد و حداقل شامل:
- commit پایه،
- branch/commit مقصد،
- فایل‌های تغییرکرده،
- علت و خلاصه تغییر،
- تست‌های اجراشده و نتیجه،
- تست‌های باقی‌مانده و علت آن‌ها.

نسخه‌ای که فقط داخل ChatGPT باقی مانده و خروجی قابل بازیابی ندارد، تحویل‌شده محسوب نمی‌شود.

## مسئولیت اعضا

**جلال:** هدایت فنی/محصولی، کنترل محدوده و تأیید مسیر تحویل.

**جواد:** توسعه Web/Desktop/Mobile، UI، integration و آماده‌سازی خروجی نهایی قابل ذخیره.

**حسن:** Backend/Database/API، تست، بررسی مستقل و آماده‌سازی خروجی نهایی قابل ذخیره.

هر سه عضو موظف‌اند همین روش را در تمام وظایف خود رعایت کنند.

## ممنوع

- توقف توسعه فقط به‌دلیل خرابی Runner یا CI.
- استفاده از GitHub به‌عنوان تنها محیط کدنویسی و تست.
- بازگرداندن کد ناتمام به GitHub به‌عنوان نسخه نهایی.
- ادعای موفقیت تست اجرا‌نشده.
- تغییر کد برای پنهان کردن مشکل زیرساخت.
- از دست دادن نسخه اصلاح‌شده داخل ChatGPT بدون خروجی قابل بازیابی.
- مخلوط کردن نتیجه فنی کد با وضعیت زیرساخت.

## قاعده حاکم نهایی

**تمام کارهای کدنویسی و تست روزانه پروژه ابتدا در ChatGPT انجام و تکمیل می‌شوند؛ پس از اتمام وظیفه و انجام کلیه تست‌های مربوط، نسخه نهایی به GitHub بازگردانده و ذخیره می‌شود.**

این اصل، نسخه اجرایی و دائمی «اصل تداوم توسعه» برای جلال، جواد و حسن است.
