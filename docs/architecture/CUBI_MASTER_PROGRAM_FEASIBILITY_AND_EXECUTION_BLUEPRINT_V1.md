## 1. Program-level feasibility conclusion

The full register is feasible as a modular, versioned product if the current single-owner boundaries are enforced. It is not feasible or safe as one monolithic implementation or a set of cloned Cloud-style apps. Delivery must be incremental, contract-first and evidence-gated.

The repository already contains substantial foundations: a shared scheduling/calculation core; project, WBS, activity, relationship, constraint, resource, cost/progress and risk APIs; an authenticated Engineering workspace; security-profile/OBS work; generic Enterprise task foundations; Form Builder and learning-memory foundations; localization resources; and Flutter/Windows client architecture work. These are not accepted as complete merely because files, schemas or PRs exist. Each is a reuse candidate requiring exact-main and exact-head audit.

**Primary architecture:** domain-owned application services over repository ports and versioned HTTP contracts; SQLite for supported local/native use and PostgreSQL for server use; server-derived tenant/actor authorization; optimistic revision checks; idempotent commands; append-only audit; immutable calculation/run snapshots; background jobs for long-running work; and typed cross-domain references rather than shared ORM entities or cross-database joins.

**Calculation rule:** Engineering Shared Domain/Calculation Core remains the sole authority for CPM, calendars, project resource assignments/leveling, cost, progress, EVM and project risk/Monte Carlo. Enterprise consumes versioned, revision-pinned Engineering facts and owns only portfolio/workforce/strategic decisions and envelopes. Workbench owns no business data or calculation.

**Client rule:** Web is online-first. Flutter and Windows clients use the same versioned application/domain contracts with local persistence, deterministic calculations where permitted, queued commands, sync cursors, conflict resolution and explicit offline capability boundaries. Never fork calculation semantics by client.
